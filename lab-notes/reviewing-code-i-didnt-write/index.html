How I Review Code I Didn't Write

November 2026

AI is a big part of how development runs at Checkout.com. So I need a process that does two things. A, it writes the code I need. B, it lets me review that code without reading a 1,000-line diff.

To help with B, I built a Claude plugin called Walkthrough. It's public, and most of this post is about how I use it.

A Ticket, Start to Finish

I have Claude Code environments set up, which makes it easy to open a chat inside a specific service or repo with the context it needs already added. On my work machine that's always the Claude desktop app, in the Code tab.

Honestly, most of the time it's as simple as this. I give Claude the ticket and tell it to plan with a bigger model (Opus or Fable), then spin up Sonnet models to do the coding. If I have extra context, like something from a call or a meeting about the ticket, I send that along with it. Then I let Claude do its thing.

About 90% of the time it picks a very good approach. It follows the conventions that have been set in the codebase since probably before Claude was a thing, and it adds the steps that are needed.

Once the code is written, I get it to run Walkthrough. That's my self-review, and I'll get to how it works in a second.

When the self-review is done, I break the ticket into the commits it needs, and sometimes into separate PRs, ready for stacks (which I hate, by the way). It gets pushed to GitHub, if GitHub isn't down that is. From there someone reviews it. If changes are needed, I ask Claude to make them and update the walkthrough, and that's about it. There are testing steps in there too that make sure the service works as expected, but I can't really talk about those.

Why Not Just Read the Diff?

A diff, in my opinion, is just hard to read. It goes file by file and line by line. When a change spans multiple files, with functions calling each other all over the place, there's no easy way to follow the process.

Say you're trying to follow how a command for a Discord bot goes from you calling it to it running and responding. There are probably several functions the command calls, sitting in separate files. In a diff view you're jumping between files by hand and trying to remember where you are. A walkthrough follows the whole execution for you, and explains it step by step.

What Walkthrough Actually Does

Walkthrough turns a big pile of context into a simple, interactive HTML page that I read in my browser. That context can be code, a stack of PRs, AI-generated changes, a design doc or a wiki page. Claude writes the walkthrough as Markdown that points at the real files and lines, and a script builds it into one self-contained page with the code highlighting and notes already built in.

It picks one concrete example, like one request or one command, and follows it through every section. Each section highlights and pins the exact lines it's talking about, so the explanation points at the code instead of describing it. Every term gets defined once, with a hover definition everywhere else, and there's a reader level (beginner, familiar or expert) depending on how much I already know.

The part I actually built it for is the notes. While I'm reading, I can select any sentence or click any code line and leave a note. There are three kinds:

Explain better rewrites that part of the walkthrough the way I ask. Change it is a review comment on the code itself: Claude changes the code, then updates the walkthrough. Question gets an answer as a reply.

When I'm done, I open the Notes panel and hit Copy for AI, paste it into Claude, and it applies the notes and rebuilds. Every note shows Claude's reply, resolved notes turn grey, and changed sections get an Updated badge. Then I read it again. That loop repeats until I'm happy.

Those screenshots aren't from work. They're from a walkthrough of this site's own code: the diff-order toggle above, which Claude wrote for this post. You can open the full walkthrough and poke around it yourself.

What I Actually Catch

Claude has a habit of over-engineering sometimes. It'll overcomplicate things that don't need it, so I have to go back and ask it to simplify, or to use another method. There was one ticket where it didn't follow the Result pattern we use in our codebase, and that one took 5+ rounds of self-review before it was ready to go.

On the opposite end, some of the names it chooses aren't descriptive at all. One word for a function that's doing a lot of things. It'll create a function called check that's actually validating keys, or doing complex regex checks. So a lot of my review notes are "rename this", or "make sure the function name actually describes what it's doing".

How many rounds it takes depends on the ticket. An entirely new feature that's quite large can take anywhere between 1 and 5 rounds before it's ready for review, and it really varies. A small bug fix can usually go with no extra changes, or maybe one more round.

Has a walkthrough ever saved me from something embarrassing? Not really. I'm a graduate, so I get a lot of support on the tickets I work on. Before I even start coding, I'm given potential approaches and things to look at, which helps make sure Claude and I take the right approach. And if I do take a wrong one, it's not embarrassing, because my team knows I'm new and they'll point me down another avenue. I'll update this when something embarrassing does happen.

"AI Wrote It, So You Don't Understand It"

I think people who hate on AI in coding have confused what AI-assisted development actually means, and I think the term vibe coding has made it worse. People see "AI was used" and assume no review happened, and that it's slop someone one-prompted and published.

I don't blame them. There are very real examples of someone one-prompting literal bullshit that probably breaks about 50 different security, privacy and data-handling laws, with terrible output to match. But that doesn't mean every AI-assisted project is like that. AI is a tool, and used properly it can produce truly great projects. It's just also been handed to people who have no clue what software engineering is, and that's how we end up with "Claude has just replaced software engineers" tweets and one-prompt projects.

At Checkout.com we all use AI, and we've been vocal about it on our blogs and on LinkedIn. My reviewers know, and I've reviewed AI-written code myself. As long as the output was properly self-reviewed first, I don't see an issue with it.

Full disclosure, then: this post was partly written by AI, so I could show the skill off. Before it went up, I went through it and changed it so it makes sense and sounds like me, not verbose AI slop. Same process as everything else.

Work vs. Personal

I use a similar loop on my personal projects. Walkthrough is the finalised version of what I want everywhere, and I'm testing it in different places right now.

I do trust AI a lot more on personal projects, though, mainly because they're less impactful. I don't handle anyone's money, and most of my projects don't involve any data handling on my side, so there's less to worry about. At worst, if the AI's code is broken, an app crashes for a moment or a bot doesn't respond in time.

At work, I'm responsible for code that handles billions of dollars a year. That's why the AI's output gets properly vetted before it goes anywhere near production.

Try It

Walkthrough is on GitHub. In Claude Code:

/plugin marketplace add heet-patel-cko/walkthrough
/plugin install walkthrough@walkthrough

Then ask for /walkthrough:create what you just built after your next AI-written change, and actually read it.
