How the diff-order toggle works

The demo in "I Don't Read Diffs Anymore", written by Claude for this post

Version 1 · familiar

In short

The toggle shows five made-up files in two orders: alphabetical, the way a diff lists them, and the order the code runs, the way a walkthrough reads them. Clicking a button really moves the list items in the page, then animates each one from where it was to where it is now. All the styling for the second order hangs off one class, run, on the figure.

What you're about to read

This covers the demo in the middle of the post: the markup, the 20 or so lines of JavaScript that drive it, and the CSS that changes when you switch. It's for someone who knows HTML, CSS and JavaScript but hasn't seen this site's code.

We'll follow one click the whole way through: a reader clicks "Walkthrough order", and commands/slowmode.py moves from third place to first.

Two ideas matter before the code:

  • The reorder is real. The items move in the page, not just on screen, so the order a screen reader announces matches the order you see.
  • The animation is a FLIP. The browser jumps the items to their new places, then each one is drawn back where it was and slides home.

The example is made up

The five files and their line counts are invented to make the point. They aren't from Serenity or any other real project.

Switching order

notes.js
355document.querySelectorAll("[data-order]").forEach((fig) => {
356 const list = fig.querySelector(".order-list");
357 const items = [...list.children];
358 const buttons = fig.querySelectorAll("[data-mode]");
359 const show = (mode) => {
360 const before = new Map(items.map((li) => [li, li.getBoundingClientRect()]));1
361 const sorted = mode === "run" ? [...items].sort((a, b) => a.dataset.run - b.dataset.run) : items;2
362 list.append(...sorted); // real DOM order, so screen readers get it too3
363 fig.classList.toggle("run", mode === "run");4
364 buttons.forEach((b) => b.setAttribute("aria-pressed", b.dataset.mode === mode));5
365 if (reduceMotion) return;
366 sorted.forEach((li) => { // FLIP: start where it was, glide to where it is now
367 const a = before.get(li), b = li.getBoundingClientRect();

370 { duration: 650, easing: "cubic-bezier(0.16, 1, 0.3, 1)" });
371 });
372 };
373 buttons.forEach((b) => b.addEventListener("click", () => show(b.dataset.mode)));6
374});

6 wires both buttons to show(), passing the button's data-mode. Inside it, 1 records where every item is on screen before anything moves. 2 picks the new order: sorted by data-run for the walkthrough order, or the original alphabetical list. 3 moves the items in the page; append moves an element that's already in the list instead of copying it. 4 adds or removes the run class that the CSS keys off, and 5 updates which button shows as pressed.

Why keep the original items array?

items is captured once, in alphabetical order, and never sorted in place (the sort works on a copy, [...items]). So switching back to diff order is just appending items again. There's no need to store the original order anywhere else.

Following the click

sorted comes back as slowmode.py, checks.py, activity.py, db.py, responses.py. append moves slowmode.py to the top, and the figure gets the run class.

1 skips the animation entirely for people who've asked their system for less motion. The items still reorder, they just don't slide. For everyone else, 2 measures where each item ended up, and 3 works out how far it moved. 4 starts it back at its old position and animates it to none, which is its new position.

Why animate transform instead of top?

Animating transform doesn't make the browser recalculate the layout on every frame, so it stays smooth even while five items move at once.

Following the click

slowmode.py moved up two rows, so dy is positive: about two rows. It starts that far below than its new home and slides up into first place over 650ms.

Where reduceMotion comes from

It's defined once near the top of the file and shared with the zoom and tilt effects.

1 is a CSS counter that numbers each item in the order it currently sits in the page, which is why the numbers come out right after the reorder. In diff order the circle shows a grey M, like git status does for a modified file. 2 swaps that for the step number and fills the circle in, only in run order. 3 fades out the line counts, since those belong to the diff view. Decisions the AI made

These are choices in the code that the post didn't ask for.

Reordering the page, not just the picture

Why

Moving the elements in the page, instead of only moving them visually with CSS, means keyboard and screen reader users get the same order as everyone else.

Web Animations instead of a CSS transition

Why

The start position of each item is only known at the moment of the click, so it's set from JavaScript with animate(). The site already uses the same approach for its image zoom.

No step numbers in the HTML

Why

The numbers come from a CSS counter instead of being written into each item, so they can never disagree with the order on screen.

What to check when reviewing

  • data-run numbers in the markup run 1 to 5 with no gaps or repeats
  • Clicking the already-pressed button does nothing odd (it re-appends in the same order and animates nothing)
  • With reduced motion turned on, the list still reorders and the explanations still show
  • Diff order shows M markers, not step numbers
  • The toggle fits on a phone without the buttons wrapping awkwardly

Words used here

FLIP
First, Last, Invert, Play. Measure where something is, move it, then animate it from the old spot to the new one.
CSS counter
A number the browser keeps while drawing the page, which goes up by one for each element that asks it to.
Grid rows trick
Animating a grid row from 0fr to 1fr, which lets something open to its natural height smoothly.
